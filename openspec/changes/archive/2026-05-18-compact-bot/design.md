## Context

Every bot from ProjectBot onwards builds a `messages` list from `build_context(context)` and sends it to the LLM. As the session grows, so does this list. The current architecture has no mechanism for trimming it: bots are append-only, `_chat_context` only grows, and the LLM eventually receives more tokens than it can usefully use (or than the model allows).

`ContextItem` already supports `mode=DISABLED` (skipped by `build_context`) and `InjectedContent` (free-form injected text). CompactBot uses both to implement compaction entirely within the existing context layer — no new content types needed.

The `token-count-status-bar` change (precursor) provides `estimate_tokens(messages: list[Message]) -> int` which CompactBot uses to check whether the threshold has been crossed.

## Goals / Non-Goals

**Goals:**
- Summarise old context turns into a single `InjectedContent` item; disable the originals.
- Keep the token count of what `build_context` returns below `compact_threshold`.
- Work entirely within the current `list[ContextItem]` contract — no protocol changes.
- Make compaction visible in the chat log (a notice item) and in the ContextStatus bar (token count drops after compaction because DISABLED items are skipped by `build_context`).

**Non-Goals:**
- User-triggered compaction (deferred to CommandBot era).
- Formal protocol extension to `ChatParticipant` — `compact()` is an optional duck-typed method.
- Compacting across the pinned-item boundary.

## Decisions

### `compact()` is called by `ChatApp` before `on_message`, not inside `on_message`

The app owns `_chat_context`. Having the bot mutate context and return the replacement list from `compact()` means the app can update `_chat_context` before calling `on_message`. This also positions `compact()` correctly for future slash-command use: `/compact` would call the same method directly.

The app triggers it via `hasattr(participant, 'compact')` — same duck-typed optional-hook pattern used by `startup` and `register_guard`.

### The bot decides whether to compact, not the app

`compact()` receives the full context and returns it unchanged if the token count is below threshold. The app always calls `compact()` if the method exists — it doesn't need to know the threshold. Threshold is a bot constructor argument sourced from `compact_threshold` in `codemoo.toml`.

This keeps the app trigger general (one line, no threshold logic) and the policy in the bot.

### Keep the last 30% of the threshold as verbatim recent context

After compaction, the context should contain: the new summary item + the most recent items totalling ≤ 30% of `compact_threshold` tokens. This leaves 70% of the budget for the session to grow before the next compaction fires. The 30% figure is configurable in spirit but hardcoded as a constant in `compact_bot.py` for now.

Pinned items (`ContextItem.pinned = True`) are never disabled, even if they fall outside the recent window.

### Summary item uses `InjectedContent` with `role="user"`

A single `InjectedContent(label="Conversation summary", text=..., role="user")` item is inserted at the position where the oldest kept item starts. This looks natural to the LLM: user-provided context about what happened before. The summary is generated by a separate LLM call with a focused prompt.

Alternatives considered:
- **In-place `SUMMARY` mode on each old item**: Produces many fragmented summaries interspersed in context — harder for the LLM to use than a single coherent block.
- **`role="assistant"`**: Could cause role-alternation issues if the immediately preceding item is also assistant. `"user"` role is safer.

### Summary prompt elides tool call traces, preserves decisions and file paths

The summarisation LLM call receives the old items rendered as plain text and is instructed to preserve: decisions made, files created or modified, explicit user instructions, open questions. Tool call/result pairs are explicitly excluded — they can be re-derived by re-running tools if needed. This keeps summaries compact.

### `_summary` is reset in `startup()`

`startup()` is called both at initial bot load and on Ctrl-R restart (which also clears `_chat_context`). Resetting `_summary = None` there ensures the two stay consistent.

### `compact_threshold` defaults to `8000` tokens in demo variants

This is well below Claude's 200k context limit but large enough to require a realistic number of turns. The demo can lower it further in the `[bots.CompactBot.variants.code]` config without changing code.

## Risks / Trade-offs

- **Two LLM calls in one turn**: When compaction fires, `compact()` makes one summarisation call before `on_message` makes the main call. This doubles latency for that turn. Mitigation: compaction fires infrequently (once per session in a normal demo); the ThinkingStatus spinner covers the wait.
- **Summary quality**: If the summarisation prompt produces a poor summary, the LLM loses context. Mitigation: keep the recent verbatim window generous (30% of threshold) so the most recent turns are always intact.
- **tiktoken approximation**: Token estimates are ±10%. Mitigation: the threshold is a soft trigger, not a hard limit. Even at 110% of estimate, the context is well within Claude's 200k window.
